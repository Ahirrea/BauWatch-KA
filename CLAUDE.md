# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

BauWatch-KA ("Wo wird gebaut?" — German for "Where's it being built?") is a purely static map/list view of the
open construction sites in Karlsruhe. No server, no backend, no running costs
(GitHub Pages). Repo language (code comments, commits, internal docs): English,
since 2026-07-27 — see the note under "Further reading" for what that switch
does and doesn't cover.

## Commands

- `npm test` — runs all test scripts in sequence (transform, build-data, diff, changelog-feed, classify, quality, pwa, attribution, rechtstexte, i18n, theme).
- Run a single test: `node scripts/test-transform.mjs` (similarly `test-build-data`, `test-diff`, `test-classify`, `test-quality`, `test-pwa`, `test-attribution`, `test-rechtstexte`, `test-i18n`, `test-theme`).
- `scripts/test-build-data.mjs` covers the **dedup and area logic** (A-7) by importing `dedupeFeatures()`/`buildFeature()`/`buildArea()` from `build-data.mjs` directly — the module only runs `main()` when started as a script, so importing it never fetches. That's the pattern for testing anything else in there: export the pure part, don't reach for the network.
- `node scripts/render-icons.mjs` — renders `icons/*.png` from `icons/icon.svg` (needs `node_modules`, uses the existing Chromium). **Manual, deliberately not in `npm test` and not in the Action** — the PNGs are committed assets, not a build artifact.
- `node scripts/screenshot.mjs` — generates `docs/showcase/*.png` for the showcase entry in the transparency portal (also manual, not in CI). Needs egress to the OSM tiles; **aborts if no tile was loaded**, instead of silently writing a gray map image. If the app's host (`tile.openstreetmap.org`) is blocked by policy but a subdomain mirror (`a.`/`b.tile.openstreetmap.org`) is reachable, the script fetches tiles from there — useful to know, because allowlists often diverge here. `src/app.js` stays untouched by this.
- `npm run build:data` (= `node scripts/build-data.mjs`) — pulls the live data and builds `data/baustellen.geojson`. **Needs network access to `mobil.trk.de`**; blocked by egress policy in some environments (the GitHub Action runners reach it). The `--allow-empty` flag forces a write even with 0 matches.
- View locally: `python3 -m http.server 8080`, then `http://localhost:8080`. **No build step for the frontend** — plain static files. Because of ES modules (`type="module"`) it must be opened over HTTP, not via `file://`.
- Node ≥ 18 required (global `fetch`). The `devDependencies` (proj4, leaflet, playwright-core) are pure dev tools; `node_modules` is not shipped.

## Architecture — the big picture

**Static hosting with a periodic data snapshot** (see `docs/ADR-001-statisches-hosting.md`). The city's WFS endpoint sends no CORS headers and is too large to fetch directly. So a **GitHub Action** takes on the role of the server:

```
City WFS ─(Action: scripts/build-data.mjs, every 4 h)→ data/baustellen.geojson (committed)
                                                              │ Browser loads static file (same origin)
                                              index.html + src/app.js → map + list
```

**The shared library `src/lib/` is the core of it.** `transform.js`, `classify.js`, `format.js` are **pure, DOM-free, dependency-free ES modules** and are imported by **both** sides: the Node build script and the browser client. This property is a hard constraint — no `document`/`window`, no npm import in `src/lib/`, or either the build or the client breaks. `src/lib/i18n.js` (A-5, client-only) holds the same property but is imported only by `src/app.js` — nothing on the build side needs UI strings.

**Data pipeline (`scripts/build-data.mjs`):** fetch WFS (several version variants with fallback) → filter to `gemeinde="Karlsruhe"` → **deduplicate by `vorgangsnummer`** → transform coordinates EPSG:25832→WGS84 → clean up/classify fields → write lean GeoJSON. Helper modules: `diff-data.mjs` (change comparison), `quality-report.mjs` (data quality).

**Client (`src/app.js`):** loads `data/baustellen.geojson`, renders a Leaflet map + synchronized list, filters (time period/closure severity/mode of transport), Nominatim radius search. Leaflet is **bundled locally under `vendor/leaflet/` (no CDN)** — `vendor/leaflet/` is the source of truth for the frontend, not `node_modules`.

**PWA (A-3):** `manifest.webmanifest`, `icons/`, and `sw.js` live in the repo root and are ordinary static files (ADR-001 stays untouched). The service worker keeps the app shell **cache-first**, but the data snapshot **network-first** — only that keeps the success criterion "never older than the last Action run" valid. On a network error it answers from the cache and sets the header `X-Bauwatch-Cache: hit`; `loadData()` reads it and marks the state as offline (deliberately **not** `navigator.onLine` — captive portals falsely report "online"). The registration is progressive enhancement: without a service worker, the page behaves exactly as before.

## Non-obvious pitfalls (important)

- **Requirements go through `docs/PROZESS.md`, not directly into code.** A non-trivial idea — even phrased as a question ("Could we do X?") — gets refined first: survey of the current state, tensions with the non-goals in `docs/PRD.md`, options with a recommendation, decisions on open forks left to the idea's originator, **its own file** `docs/anforderungen/A-<no.>-<short-title>.md` (from `docs/anforderungen/_vorlage.md`) + a line in `docs/anforderungen/README.md` (that's where — and **only** where — the status lives). **Implementation starts only on an explicit green light** — a pre-chosen feature branch name is not one. Small fixes and technical tasks still go directly through `docs/BACKLOG.md`; the dividing line is in the process ("Requirement or task? The test"). Architectural decisions additionally get an ADR under `docs/entscheidungen/` — this folder is **append-only**, an ADR is never rewritten.
- **This translation kept file and folder names as they were.** `docs/PROZESS.md`, `docs/anforderungen/`, `docs/entscheidungen/` still carry their German names — only the prose inside was translated. Renaming was out of scope: `.claude/commands/anforderung.md` hardcodes these exact paths and is itself written in German (`Sprache: Deutsch`), so a rename would silently break that command. Don't rename these folders/files without updating that command file in the same pass. Both files under `.claude/commands/` are still German, and `reflect.md` additionally prescribes a *German* commit message — that predates the 2026-07-27 switch, so the English rule below wins: follow a command's steps, not its language.
- **Deduplication must run on `vorgangsnummer`, not on `id`.** Every case delivers a point and a polygon as two features with *different* per-geometry `id`s but the same `vorgangsnummer`. Deduplicating on `id` doubles every entry (440 instead of 186).
- **Real WFS field names** (don't guess): `vorgangsnummer`, `vorgangszeitraum_von`/`_bis`, `lage`, `art`, `verursacher`, `zusatzinfo`, `sperrung`, `gemeinde`. `art` already contains **plain text** (no cryptic codes); `classifyArt` takes readable values as-is. The official field **`sperrung` is authoritative for the traffic-light status** — free text must not override it.
- **The real WFS geometry mix, measured (A-7, inspection run 2026-07-28).** Don't re-derive this from feature counts — 444 Karlsruhe features / 183 cases looks like "~2.4 geometries per case", and reasoning from that with the natural assumption of *one point per case* gives badly wrong conclusions. The actual shape: **222 Points and 222 non-Point geometries, exactly paired.** 159 cases carry one point + one shape; 24 cases carry 2–6 of *each* (a closure split across several street segments or building entrances). Types: `Polygon` 156, `MultiLineString` 36, `MultiPolygon` 22, `LineString` 8 — so **~20 % of shapes are line geometries, not areas**, which Leaflet draws as polylines that ignore `fillOpacity` entirely. `data/QUALITY.md`'s `hasArea` line tracks the ratio going forward; the type mix needs a fresh inspection run if it matters again.
- **What the shapes actually look like** (first full build with `area`, 183/183 cases): **no shape is an axis-aligned rectangle — 0 of 230 polygon rings.** They're oriented to the street. Vertices per ring: min 4, median 6, max 180; 114 rings have exactly 4 corners and 78 of those are right-angled, i.e. *rotated* rectangles (a lane or sidewalk strip), while 82 rings carry 11+ vertices and are genuine outlines. So a synthetic test fixture built from grid-aligned boxes looks nothing like production — if you fake `area` data for a browser check, rotate it, or you'll be reviewing a picture the app will never draw.
- **The WFS delivers *two* geometries per case, and both are now kept (A-7).** Before A-7 the dedup loop threw the polygon away; now `dedupeFeatures()` keeps the Point as `geometry` (marker position, unchanged) **and** *all* sibling non-Point geometries, combined by `buildArea()` into one `properties.area` (`MultiPolygon` if all polygonal, `MultiLineString` if all linear, `GeometryCollection` if mixed; a lone shape is left alone). Three things follow. (1) **`geometry` stays a `Point`, always** — `latLngOf()`, `haversineKm()`, the radius search, the filters, and the list all read the point and nothing else (E1 in A-7); putting a polygon in `geometry` would touch every one of them. (2) **`transformGeometry()` transforms unconditionally**, unlike `toWgs84()`, which auto-detects via `looksLikeUtm32`. `buildArea()` therefore does that check itself before calling it — drop the check and a source that unexpectedly answers in WGS84 gets its area mangled while its point comes through fine, i.e. a bug visible only on the map. (3) `properties.area` is the one **English** property name on a feature otherwise full of German ones (`titel`, `verursacher`, `ampel`) — deliberate (E7), new identifiers are English since 2026-07-27; don't "fix" the inconsistency in either direction.
- **Leaflet's popup `autoPan` silently overrides `fitBounds` (A-7/E5).** `selectFeature()` fits the map to a case's area and *then* opens the marker popup. Opening it pans the map so the popup sits at the **map** edge — a pan computed from the popup and marker alone, which lands in the same place no matter what the fit just did. Measured: up to ~200 px of shift, pushing 25–50 m of the just-fitted shape back out of view. Two consequences. (1) Markers on features that *have* an area are bound with `{ autoPan: false }`; point-only markers keep the Leaflet default, where autoPan is genuinely useful because `setView()` only centres the marker and reserves no room. (2) `fitBounds()` reserves that room itself via `paddingTopLeft` (`AREA_FIT_POPUP_ROOM`, capped at a share of the map height so a phone doesn't lose its whole map) — delete the reservation and the popup gets clipped instead of panned. Symptom to recognise: *identical* measured bounds before and after changing the fit padding means autoPan won, not that your change didn't apply.
- **A new feature property is invisible until the next real data change.** `diffFeatures()`/`signature()` compare all non-`_` properties, so adding `area` does count as a change and *does* trigger a write — but only on the next Action run, and the changed cases land in `data/CHANGELOG.md` with the generic note (the "Was ist neu?" feed drops them, per #28 — which is exactly right here: a schema addition is not news for a resident). The committed snapshot is therefore **behind the code** between merge and that run, and the client must tolerate it: `renderAreas()` skips a feature without `area`, `selectFeature()` falls back to today's `setView`. Adding a property that the client *requires* would need the snapshot rebuilt in the same commit — see the read-side-filter pitfall below for the mirror-image case.
- **Commit only on a real data change.** `build-data.mjs` compares against the previous snapshot and only writes/commits when features change. `stand` = the time of the last *change*, not of the last run. Consequence: the Git history of `data/baustellen.geojson` = real changes; many Action runs + few commits = changes are rare. **Never write per-run-volatile values into the file** (that creates noise commits and destroys this invariant).
- **Coordinate order:** GeoJSON is `[lon, lat]`, Leaflet expects `[lat, lng]`. The build has CRS auto-detection (`looksLikeUtm32`) and only transforms when values look like UTM meters.
- **The CC-BY attribution is static in `index.html` — not set via JS.** It used to be an empty paragraph that `setFooter()` filled in after the data fetch: visible in the browser, not in the served document — and absent entirely on a failed fetch or without JavaScript. As a **license condition** it must not depend on any of that (the city's open-data editorial team noticed exactly this during the showcase pre-review). The text is word-for-word identical to `ATTRIBUTION` in `scripts/build-data.mjs`; if one changes, the other must too. `scripts/test-attribution.mjs` checks all three traps (empty attribution, being overwritten by `app.js`, drift from the build constant). Additions like the sample-data notice go through the separate paragraph `#attribution-hinweis`.
- **`--amber` is not a text color.** The traffic-light colors in `src/styles.css` are tuned for markers and dots. As text on `--bg`, `--red` (~5.5:1) and `--green` (~5.0:1) meet WCAG AA, but `--amber` (`#f08a00`) only reaches ~2.3:1 **in light mode** — in dark mode, by contrast, ~9.7:1, so the violation doesn't show up at all when testing in dark mode. For warning or emphasized text, use `--accent` or `--text` instead. **Calculate, don't estimate:** in the Playwright check, open one context with `colorScheme: 'light'` **and** one with `'dark'`, get the colors via `getComputedStyle`, and compute the WCAG ratio — a visual check in only one scheme cannot catch this violation at all. **Since A-8 the scheme is switchable**, so `colorScheme: 'dark'` on the context is no longer the same thing as "the page is dark": an explicit choice (`data-theme` on `<html>`) beats the context setting. When checking colors, either set the context scheme *and* leave the toggle alone, or click the toggle and ignore the context — reading `getComputedStyle(document.documentElement)` tells you which palette actually won.
- **`--bg` is the page background, not "the subtle surface."** Elements sitting on top (badges/chips) sit on `--surface` (list card), not on `--bg`. In light mode, `--bg` (#f7f7f5) happens to fit there *by coincidence* — it's a bit darker than the white card; in dark mode, `--bg` (#16181c) is **darker than** `--surface` (#1f2329), so the chip looks punched-out instead of resting on top (Backlog #22). That's why badges have their own tokens `--chip`/`--chip-border`. Pattern for new surfaces: pick or create a token by its role, not by whatever color value it happens to have in light mode — and check against the surface the element actually sits on, in **both** schemes. For dark chips, also pull the border along: `--border` (#333941) sits too close to the chip's tone and smears the edge.
- **`docs/BACKLOG.md` states status twice.** Besides the checkbox on the entry, the header has a `**Status:**` line and a "summary" that names individual numbers as open/done. Whoever only flips `⬜` → `✅` on the entry leaves a header that contradicts the entry — the same silent drift as with attribution and the privacy notice, just without a test here. A status change means: entry **and** header. (The opposite holds for `docs/anforderungen/` — there the overview is the *only* source of status.)
- **The `transform.js` reference test** checks against ground truth generated with `proj4`. `proj4` is **not a runtime dependency**, just a dev tool for generating the reference values.
- **GitHub Pages** deploys from `main`/root — every data commit goes live immediately. **Don't** switch to an Actions-based Pages deployment (that would serve snapshots → stale data). It's served under a **sub-path** `…github.io/BauWatch-KA/`, not at a domain root: paths in HTML/CSS/JS and in new assets must stay **relative** (`vendor/…`, not `/vendor/…`) — a leading `/` points at the `github.io` root and breaks silently.
- **`navigationAntwort()` in `sw.js` answered *every* navigation with `index.html` until A-4.** For a single-page app that was correct; with `impressum.html`/`datenschutz.html` it would have become a **silent bug** — installed clients would get the map page under `…/impressum.html`, with no error, and **locally this never shows up** (no old service worker registered). Since [ADR-002](docs/entscheidungen/ADR-002-mehrseitige-auslieferung.md), the function is **path-aware**: first the requested path from the shell cache, then network, `INDEX_URL` only as an offline fallback. Consequence: **every new HTML page must be in `SHELL`** (otherwise it's gone offline *and* not path-aware discoverable). `scripts/test-pwa.mjs` checks path-awareness statically and now scans **all** precached HTML pages for precache gaps, not just `index.html`.
- **The privacy notice is a claim about the code — and goes stale silently.** `scripts/test-rechtstexte.mjs` guards both directions: every external host from `src/*.js` must be named in `datenschutz.html` (build `routing.openstreetmap.de` for A-1 without updating it → `npm test` goes red), and as long as it states "no cookies / no own storage of personal data," neither `document.cookie`, `sessionStorage`, `indexedDB`, nor `navigator.geolocation` may show up in the frontend. Same drift logic as with attribution: a wrong privacy notice is worse than an incomplete one. The contact address is currently a **placeholder** (`kontakt@example.invalid`) — allowed as long as `docs/showcase-einreichung.md` lists it as an open item; if that gets checked off without updating the pages, the test fails.
- **`localStorage` gets a documented-key check, not an unconditional one (A-5/E6/ADR-003).** Since the DE/EN language toggle, `localStorage` is no longer categorically absent from the frontend — `test-rechtstexte.mjs`'s guard for it changed from "must not appear" into "every key found (`localStorage.getItem/setItem(...)`, resolved through a named constant like `SPRACHE_KEY` if needed) must be named in `datenschutz.html`'s 'Speicherung auf Ihrem Gerät' section." An *undocumented* key still fails the build; the other four storage checks (Cookies, `sessionStorage`, `indexedDB`, geolocation) stay unconditional, since they remain genuinely unused. Don't "fix" a red `test-rechtstexte.mjs` by weakening this back to unconditional — document the new key instead, same principle as the placeholder-address `WARN` below. **A-8/ADR-004 widened the exception** from one blessed key to a bounded *category* (anonymous display preferences, closed value set); there are now two keys (`bauwatch.sprache`, `bauwatch.theme`), and `test-theme.mjs` adds the value-level check — the *possible values* must be documented too, not just the key name. A new key of that kind no longer needs its own ADR, but it does need the privacy-notice entry.
- **The dark palette is deliberately written twice in `src/styles.css` (A-8) — don't "deduplicate" it.** It has to be reachable two ways: from `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` (nobody chose anything) and from `:root[data-theme="dark"]` (somebody did). CSS can't share one declaration block between a media query and a plain selector. Delete the media query and everyone who never touched the switch loses dark mode; delete the attribute block and the switch stops working. `scripts/test-theme.mjs` compares both blocks token-by-token and fails on drift, so *adding* a token means adding it to both. The same script guards the other three copies of a single fact: the `localStorage` key literal in `index.html`'s inline no-flash script vs. `THEME_KEY` in `app.js`, `THEME_COLOR` in `app.js` vs. the `<meta name="theme-color">` pair, and the toggle buttons vs. `THEMES`.
- **`index.html` has an inline `<script>` in `<head>` and it must stay there, before the stylesheet.** `src/app.js` is a module and therefore deferred — without those three lines, a visitor who chose dark gets a light flash on every load. It only reads the key and sets `data-theme`; anything else belongs in `app.js`. The legal pages are the opposite case: `impressum.html`/`datenschutz.html` must stay script-free (E6 in A-4, checked), which is exactly why they follow the system setting only and *don't* honor the toggle.
- **`impressum.html` and `datenschutz.html` stay German on purpose.** They're the actual site content for Karlsruhe residents, not internal docs — the 2026-07-27 docs-language switch to English covers `CLAUDE.md`/`README.md`/`docs/`, not the user-facing app itself. The manifest's `name`/`short_name`/`lang` fields stay German-only too (installed PWA identity). **`index.html`/`src/app.js` are the one exception**: since A-5, the interactive map page is bilingual via a DE/EN toggle (`src/lib/i18n.js`), German by default — see `docs/PRD.md`'s "Constraints" section and `docs/anforderungen/A-5-sprachumschalter.md` for the exact boundary (map shell in scope; legal pages, PWA identity, CC-BY attribution, and raw dataset text stay German-only, non-negotiably).
- **A guard must not permanently turn `npm test` red.** For a deliberately open item (placeholder address, still-missing detail), tie the test's strictness to the **documentation status**, not to a date or good intentions: as long as the relevant document lists the item as open, the test reports `[WARN]` and stays green; if the checkbox gets ticked there while the code still carries the placeholder, it fails hard. That way nothing goes live silently and the suite keeps its meaning.
- **A "this string must not appear here" guard also matches comments.** Several tests assert the *absence* of a literal (a second copy of the generic changelog note in `app.js`, `document.cookie`/`sessionStorage` in the frontend). An explanatory comment that quotes the string turns them red — that's correct behaviour, not a false positive, since the whole point is that the literal lives in exactly one place. Reference the **constant's name** in comments (`GENERIC_CHANGE_NOTE`), never its value.
- **Shell file changed → bump `CACHE_SHELL` in `sw.js`.** The service worker precaches the app shell (`index.html`, `src/*`, `vendor/leaflet/*`, `icons/*`, manifest) **cache-first and all-or-nothing per version**. Whoever touches one of these files without bumping the version serves installed clients the old version indefinitely — locally this never shows up. The `SHELL` list in `sw.js` is hand-maintained; a single typo in it makes `cache.addAll` fail entirely, and the SW then never installs. `scripts/test-pwa.mjs` checks both (existence of every entry, version in the cache name) plus the classic precache gap: every reference from `index.html` **and** every relative import from `src/app.js` must be in `SHELL`. Currently `v11` (A-7's area layer changed `src/app.js`; `v10` added `src/lib/changelog.js` to `SHELL` for #28; `v9` was A-8's colour-scheme switch). Note that a requirement doc can name a stale target version — `A-7-baustellenflaechen.md` says "`v6` → `v7`" because that was current when it was written; the bump is always *from whatever `sw.js` says today*, not from the number in the doc.
- **The feed shows *less* than `data/CHANGELOG.md`, on purpose (#28) — that asymmetry is the feature, not drift.** A case that changed only outside `WATCH_FIELDS` (coordinates, `art`, mode of transport) gets the fallback note `sonstige Angaben aktualisiert`. In `data/CHANGELOG.md` that belongs — it's the record of what the data did. In "Was ist neu?" it can't answer the app's question ("does this affect me?"), and whole runs consisted of nothing else. So `changelogEntry()` drops those changes, `build-data.mjs` skips an entry left empty by that (otherwise the dialog shows a timestamp with an empty list), and `src/app.js` filters again **on read** — that's what cleans the entries already committed inside the 30-day window and any copy an installed service worker still holds. Parity between the two artifacts is therefore **directional**: feed ⊆ Markdown, checked that way in `test-changelog-feed.mjs`. Don't "restore" the symmetry. The literal lives **once**, in `src/lib/changelog.js` — a shared pure module in the `transform.js`/`classify.js` sense (imported by the Node build *and* the browser), so it's bound by the same no-DOM/no-npm constraint and is in `SHELL`; a second copy of the string in `app.js` fails the test.
- **`data/changelog.json` (A-6) — same anti-drift/no-volatile-value rules as `CHANGELOG.md`/`QUALITY.md`.** Written by `build-data.mjs` in the same `hasChanges(diff)` branch as `prependChangelog()`, via the pure `changelogEntry()`/`pruneChangelogEntries()` helpers in `scripts/diff-data.mjs` (kept there, next to `summaryMarkdown()`, so the two artifacts can't drift). `stand` is the real change timestamp, never the run time — same invariant as `baustellen.geojson`'s own `stand`. Pruned to the last 30 days on every write; a `firstFill` run collapses to one synthetic `{ stand, firstFill: true, total }` entry instead of flooding the feed. `sw.js`'s data-path handling now covers **two** files (`DATA_PATHS` — `baustellen.geojson` and `changelog.json`), both network-first; `changelog.json` is deliberately **not** prefetched at service-worker install time (unlike `baustellen.geojson`) and is **not** part of `SHELL` — it's data, not shell.
- **Narrowing what a committed data artifact may contain needs a read-side filter too — and the existing file cleaned in the same commit.** `data/changelog.json` and `data/baustellen.geojson` are committed snapshots with their own retention (30 days) and are cached by the service worker, so a change to what the *build* emits stays invisible for up to that window — longer for installed clients. Pattern (#28): filter on write **and** on read through the same shared pure helper, then run the committed file through that helper in the same commit. A hand-touched data file is the deliberate exception to "data commits come from the Action"; the alternative is shipping a repo whose data contradicts the app.
- **`data/QUALITY.md`'s `hasArea` line is an observation, not a defect count (A-7/E9).** Every other block in the quality report lists something *wrong* with the city's data; "Vorgänge mit Fläche" / "Vorgänge ohne Fläche" just reports the geometry mix, because whether a case really pairs one point with one polygon **can't be checked outside an Action run** (egress). So don't fold `ohneFlaeche.length` into `summarizeQuality()`'s `problems` total — a point-only case renders exactly as it did before A-7. `mitFlaeche` is derived (`total − ohneFlaeche.length`), and `test-quality.mjs` asserts the two add up to `total`, so a future `hasArea` change can't silently produce a ratio that means nothing.
- **The service worker is only testable via `localhost`** (secure context) — `file://` doesn't register. Playwright pattern: `context.setOffline(true)` does **not** reach `fetch` calls from inside the service worker (its own network context); for a real offline test, cut off same-origin via `context.route(…, r => r.abort())`. The update-banner path can be run end-to-end by copying the project to the scratchpad, serving from there, and bumping `CACHE_SHELL` in the copy.
- **The very first page load bypasses the service worker** (no `controller` yet) — that's why the `install` handler loads `data/baustellen.geojson` into the data cache once, itself. Without this step, after a single visit the shell would be ready offline but not a single construction site would be.
- **No `push`/`notificationclick`/`sync` handler in the SW.** The SW is the technical prerequisite for push — the non-goal "no real push" (`docs/PRD.md`, decided in `A-2`) still holds; `scripts/test-pwa.mjs` checks the absence of these handlers.
- **Sample-data starting value:** `data/baustellen.geojson` can carry `sample: true`; the first real Action run replaces it (`firstFill` logic).
- **The data Action commits to `main` itself.** After a manually triggered run (or while working in parallel), the local state goes stale quickly — before the next push, run `git pull --rebase origin main`, or the push gets rejected with "fetch first".
- **The real WFS structure can only be checked via an Action run** (local fetch is blocked by egress). Pattern for schema/field-name questions: run a small inspection script via a temporary `workflow_dispatch` workflow, read the job logs, then remove it again.

## Testing the frontend in a browser

`playwright-core` is installed; Chromium lives under `/opt/pw-browsers/chromium-*/chrome-linux/chrome` (with `--no-sandbox`). **Glob it, don't hardcode the build number** — the pinned `@playwright/test` version and the image's Chromium build drift apart, and a stale path fails with "executable doesn't exist". Pattern: start a local `http.server`, load the page, wait for `#liste li`. In environments without egress, intercept OSM tiles via `page.route('**://tile.openstreetmap.org/**', r => r.abort())` — the map then stays gray, markers/list/filters still work (markers are SVG `circleMarker`s, they don't need tiles).

Two traps when asserting on the map's SVG (both cost a debugging round during A-7):

- **`#map svg path` is not "the map's shapes."** Leaflet's attribution control carries a three-`<path>` Ukraine-flag SVG, so any count or "every stroke is an ampel colour" assertion over that selector is off by three and sees a `null` stroke. Scope to **`.leaflet-overlay-pane svg path`**, and separate markers from areas by `classList.contains('leaflet-interactive')` — the area layer is `interactive:false` (A-7/E3) and therefore has no such class. That distinction is also the cheapest way to *check* E3.
- **Don't infer zoom from pixel sizes.** `src/app.js` keeps the Leaflet map in a module-scoped `map`, invisible to `page.evaluate`. Rather than measuring a shape's on-screen width (fragile — the widest shape after a `fitBounds` is often a *neighbouring* one), grab the instance from the test side with `page.addInitScript()` wrapping `L.map` to stash it on `window`: then `getZoom()`/`getBounds()` answer directly, which is what makes A-7's `maxZoom:17` cap actually assertable. The app stays untouched.
- **Compare pan/zoom against the `before/` checkout, not against intuition.** Leaflet's popup `autoPan` shifts the centre when the popup wouldn't fit, so "selection didn't centre exactly on the marker" can be pre-existing behaviour that depends only on the zoom you happened to arrive at. Load both checkouts from the same start view and diff `getCenter()`/`getZoom()`.
- **Never select a list item by title substring.** Construction-site titles are not unique (several `vorgangsnummer` share one street description) and the default "heute aktiv" filter hides some, so `innerText.includes(title)` can click a *different* feature — and then a geometry assertion measures a shape that was never selected and reads as a code bug. Resolve the target to a **list index** in-page, require the title to be unique both in the rendered list and in the data, and assert afterwards that `#liste li.is-selected` really is the intended one. Same discipline for the map: when a check disagrees with what the code plainly does, patch `L.Map.prototype.fitBounds`/`setView` from `addInitScript` to log what they actually received before touching `src/app.js` — twice during A-7 that turned an apparent bug into a test flaw (and once into a real one).

## Web/mobile workflow (Claude Code on the web)

This repo is often worked on from a **cloud session** (claude.ai/code, including from a phone/the Claude app). On a small screen, typing and reading diffs are the bottleneck, not compute time — the following points are geared toward that:

- **Have it verified instead of scrolling diffs.** Phrase the task so Claude runs `npm test` **and** a Playwright browser check itself and only reports the result ("N/N checks green"). Pure, DOM-free logic changes in `src/lib/` are covered by `npm test`; UI/`app.js` changes additionally get checked in the browser (see "Testing the frontend in a browser"). For **doc restructuring** (moving/splitting `.md` files), `npm test` says nothing — check mechanically instead: all relative links still resolve, and no text was lost while splitting (compare sentence counts old↔new, report only intended deviations).
- **Always send screenshots along with UI changes** — unprompted, as part of the result report (explicit wish of the idea's originator). On a small screen, an image is grasped faster than any description, and visual findings ("looks punched-out") can only be signed off visually. Practice: generate Playwright screenshots in the scratchpad and send them via `SendUserFile` — **mobile (414 px) and desktop (1280 px), each light and dark** (`colorScheme`), plus a close-up of the changed element (`locator(…).screenshot()`, `deviceScaleFactor: 3`). Intercept tiles while doing so (see above) and mention when reporting that the gray map is due to that. The screenshots do **not** replace the computed contrast values, they come in addition. For a change that *removes* or filters something, a genuine before-shot is worth the extra minute: `git archive HEAD | tar -x -C <scratchpad>/before` gives an unmodified pre-change checkout, served on a second port and screenshotted with the same locator. The same trick serves the **old** data file against the **new** code — that's how you prove a read-side filter really cleans already-committed entries, instead of asserting it.
- **`node_modules` is not shipped** and is empty in fresh sessions. Before browser checks: `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install` (Chromium is already there, no need to redownload). **Afterward, remove `node_modules` again and don't commit `package*.json`** if the install touched them — they don't belong in a feature commit.
- **Temporary scripts** (e.g. verification runners) go in the scratchpad — there, import `playwright-core` via an **absolute path** (`<repo>/node_modules/playwright-core/index.mjs`). Starting from the project directory does **not** help — ESM resolves bare specifiers relative to the importing file, not to the working directory (and `NODE_PATH` doesn't apply to ESM either). Clean up afterward, never commit.
- **Mind egress.** `build:data` needs `mobil.trk.de`, radius search needs `nominatim.openstreetmap.org`, the map needs `tile.openstreetmap.org` — blocked or not depending on the environment's network policy. Intercept tiles in tests (see above); for real data runs, allow the domain in the environment's network config under "Network access → Custom", or use the GitHub Action.
- **Recommended environment configuration.** For everyday work (changing code, `npm test`, a Playwright check with intercepted tiles, committing/pushing), **Trusted** is enough — npm, GitHub, and `raw.githubusercontent.com` are in the default allowlist. Only someone running `build:data` or the live map/radius search **directly in the web session** needs **Custom** with `mobil.trk.de`, `nominatim.openstreetmap.org`, `*.tile.openstreetmap.org` (checkbox "include defaults" **on**, or `npm install` breaks). The Custom tier is only selectable via the web UI, not in the mobile "create environment" dialog.
- **Env variables: none needed.** The project uses no secrets/API keys (WFS/Nominatim/OSM are public; the only `process.env` use is the Action's built-in `GITHUB_STEP_SUMMARY`). The Playwright variables are already set by the platform image.
- **Setup script (optional):** `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install || true` pre-installs the dev deps so browser checks run immediately without manual installing. **`npm install`, not `npm ci`** — `package-lock.json` is gitignored and missing in fresh sessions. No commit risk: `node_modules/` and the lockfile are gitignored, `npm install` doesn't touch `package.json`. `npm test` itself needs no `node_modules` (plain Node scripts), the pre-install only matters for the browser checks.
- **Teleport to the right device.** On the laptop, `claude --teleport` pulls the phone session — including branch and history — into the terminal — prerequisite: same claude.ai account, clean git state, and **the branch is pushed** (the VM clones from GitHub). So: commit and push work before switching.
- **`main` moves under you.** The data Action commits to `main` itself; before pushing to `main`, always `git fetch origin main` first and rebase/cherry-pick your own commit onto it (no force-push needed if only genuinely new work is added). **Pull requests are unusual here** — finished work lands directly on `main`. Clean path for "commit directly to main" on request: commit on the feature branch, `git fetch origin main`, then **fast-forward** (`git merge --ff-only <branch>`) and push — no merge commit (the one in the history is an accidental `git pull`).
