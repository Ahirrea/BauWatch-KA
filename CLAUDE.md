# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

BauWatch-KA ("Wo wird gebaut?" — German for "Where's it being built?") is a purely static map/list view of the
open construction sites in Karlsruhe. No server, no backend, no running costs
(GitHub Pages). Repo language (code comments, commits, internal docs): English,
since 2026-07-27 — see the note under "Further reading" for what that switch
does and doesn't cover.

## Commands

- `npm test` — runs all test scripts in sequence (transform, format, build-data, diff, changelog-feed, classify, quality, pwa, attribution, rechtstexte, i18n, theme, stats, history, feed, districts). Since #36 it also runs in CI (`.github/workflows/test.yml`) on every push and pull request that touches more than `data/` — no `npm install` there, the scripts are plain Node.
- Run a single test: `node scripts/test-transform.mjs` (similarly `test-format`, `test-build-data`, `test-diff`, `test-classify`, `test-quality`, `test-pwa`, `test-attribution`, `test-rechtstexte`, `test-i18n`, `test-theme`, `test-stats`, `test-history`, `test-feed`, `test-districts`).
- `scripts/test-build-data.mjs` covers the **dedup and area logic** (A-7) by importing `dedupeFeatures()`/`buildFeature()`/`buildArea()` from `build-data.mjs` directly — the module only runs `main()` when started as a script, so importing it never fetches. That's the pattern for testing anything else in there: export the pure part, don't reach for the network.
- `node scripts/backfill-history.mjs` — rebuilds `data/history.json` from the Git history of `data/baustellen.geojson` (A-16, ADR-006). **Manual, not in `npm test`**, needs a full (non-shallow) clone. Rerun it right before landing a branch: the data Action keeps committing to `main`, and `test-history.mjs` fails while the history's last day differs from the snapshot.
- `node scripts/feed.mjs` — regenerates `feeds/alle.xml` from the committed `data/changelog.json` (A-2). The build does the same in every real-change run; run it by hand only after hand-editing `changelog.json` (a #28-style cleanup), because `test-feed.mjs` fails on any drift between the two.
- `node scripts/annotate-districts.mjs` — writes `district` into every feature of the committed `data/baustellen.geojson` from `data/districts.geojson` (A-17/E9), keeping `stand`. **Manual.** Rerun it right before landing a branch, like the history backfill: `test-districts.mjs` fails while a feature's district differs from what the build would compute, which is what keeps the first Action run after a release from logging every case as changed.
- `node scripts/fetch-districts.mjs` — fetches the city's district boundaries and writes `data/districts.geojson` (A-17 step 1, ADR-007). **Never scheduled, and it cannot run here:** the portal is blocked by egress like the WFS. To refresh the boundaries, put the step temporarily into `update-data.yml` on a branch, dispatch that workflow with `ref=<branch>` (its commit step pushes the file to the branch), then reset the workflow file to `main`'s version — exactly how the file was made on 2026-10-18.
- `node scripts/render-icons.mjs` — renders `icons/*.png` from `icons/icon.svg` (needs `node_modules`, uses the existing Chromium). **Manual, deliberately not in `npm test` and not in the Action** — the PNGs are committed assets, not a build artifact.
- `npm run build:data` (= `node scripts/build-data.mjs`) — pulls the live data and builds `data/baustellen.geojson`. **Needs network access to `mobil.trk.de`**; blocked by egress policy in some environments (the GitHub Action runners reach it). The `--allow-empty` flag forces a write even with 0 matches.
- View locally: `python3 -m http.server 8080`, then `http://localhost:8080`. **No build step for the frontend** — plain static files. Because of ES modules (`type="module"`) it must be opened over HTTP, not via `file://`.
- Node ≥ 18 required (global `fetch`). The `devDependencies` (proj4, leaflet, playwright-core) are pure dev tools; `node_modules` is not shipped.

## Architecture — the big picture

**Static hosting with a periodic data snapshot** (see `docs/adr/ADR-001-statisches-hosting.md`). The city's WFS endpoint sends no CORS headers and is too large to fetch directly. So a **GitHub Action** takes on the role of the server:

```
City WFS ─(Action: scripts/build-data.mjs, every 4 h)→ data/baustellen.geojson (committed)
                                                              │ Browser loads static file (same origin)
                                              index.html + src/app.js → map + list
```

**The shared library `src/lib/` is the core of it.** `transform.js`, `classify.js`, `format.js` are **pure, DOM-free, dependency-free ES modules** and are imported by **both** sides: the Node build script and the browser client. This property is a hard constraint — no `document`/`window`, no npm import in `src/lib/`, or either the build or the client breaks. `src/lib/i18n.js` (A-5, client-only) holds the same property but is imported only by the client (`src/ui/`) — nothing on the build side needs UI strings. The same goes for `src/lib/stats.js` (A-10, A-12, A-15): pure and tested, used only by the browser. The UI modules in `src/ui/` are the opposite: DOM by design, and therefore never in `src/lib/`.

**Data pipeline (`scripts/build-data.mjs`):** fetch WFS (several version variants with fallback) → filter to `gemeinde="Karlsruhe"` → **deduplicate by `vorgangsnummer`** → transform coordinates EPSG:25832→WGS84 → clean up/classify fields → write lean GeoJSON. Helper modules: `diff-data.mjs` (change comparison), `quality-report.mjs` (data quality).

**Client (`src/app.js` + `src/ui/`) — a map app shell since A-14 ([ADR-005](docs/adr/ADR-005-neuaufbau-oberflaeche.md)):** the map fills the viewport and the page itself never scrolls; one panel (`#panel`) floats above it — a bottom sheet with three heights on a phone, a collapsible side panel on desktop — holding the search bar, the status line, and the tabs Liste · Statistik · Neu (filters + synchronized list; the statistics of A-15; the "Was ist neu?" feed). Settings live in a ☰ menu (`<dialog>`), the CC-BY attribution and the legal links in a static credits `<footer>` on the map. `src/app.js` is the entry module (render pipeline, selection/hover, data load, boot order); the feature modules live in `src/ui/` (state, dom, geo, text with `str()`, theme, filters, districts, feature-html, map, list, search, panel, menu, feed, stats, history, pwa) and talk through callbacks, not circular imports. `src/styles.css` holds the palette tokens, the base and the text-page rules the legal pages need; `src/shell.css` the map page's own styles (A-14/E12). Leaflet is **bundled locally under `vendor/leaflet/` (no CDN)** — `vendor/leaflet/` is the source of truth for the frontend, not `node_modules`.

**PWA (A-3):** `manifest.webmanifest`, `icons/`, and `sw.js` live in the repo root and are ordinary static files (ADR-001 stays untouched). The service worker keeps the app shell **cache-first**, but the data snapshot **network-first** — only that keeps the success criterion "never older than the last Action run" valid. On a network error it answers from the cache and sets the header `X-Bauwatch-Cache: hit`; `loadData()` reads it and marks the state as offline (deliberately **not** `navigator.onLine` — captive portals falsely report "online"). The registration is progressive enhancement: without a service worker, the page behaves exactly as before.

## Non-obvious pitfalls (important)

- **Requirements go through `docs/PROZESS.md`, not directly into code.** A non-trivial idea — even phrased as a question ("Could we do X?") — gets refined first: survey of the current state, tensions with the documented decisions (`docs/adr/`), options with a recommendation, decisions on open forks left to the idea's originator, **its own file** `docs/anforderungen/A-<no.>-<short-title>.md` (from `docs/anforderungen/_vorlage.md`) + a line in `docs/anforderungen/README.md` (that's where — and **only** where — the status lives). **Implementation starts only on an explicit green light** — a pre-chosen feature branch name is not one. Small fixes and technical tasks still go directly through `docs/BACKLOG.md`; the dividing line is in the process ("Requirement or task? The test"). Architectural decisions additionally get an ADR under `docs/adr/` — this folder is **append-only**, an ADR is never rewritten. A requirement file is *not* append-only, but a decision that implementation disproves gets **revised in place with the original left visible** (`E<n>` followed by an `E<n> revised (<date>)` block naming the evidence) — the file is the record of *why* it was solved this way, and silently rewriting a decision destroys exactly that.
- **The docs translation kept file and folder names as they were.** `docs/PROZESS.md` and `docs/anforderungen/` still carry their German names — only the prose inside was translated. (`docs/entscheidungen/` became `docs/adr/` on 2026-08-07; the former `.claude/commands/` were removed the same day.)
- **Deduplication must run on `vorgangsnummer`, not on `id`.** Every case delivers a point and a polygon as two features with *different* per-geometry `id`s but the same `vorgangsnummer`. Deduplicating on `id` doubles every entry (440 instead of 186).
- **Real WFS field names** (don't guess): `vorgangsnummer`, `vorgangszeitraum_von`/`_bis`, `lage`, `art`, `verursacher`, `zusatzinfo`, `sperrung`, `gemeinde`. `art` already contains **plain text** (no cryptic codes); `classifyArt` takes readable values as-is. The official field **`sperrung` is authoritative for the traffic-light status** — free text must not override it.
- **The real WFS geometry mix, measured (A-7, inspection run 2026-07-28).** Don't re-derive this from feature counts — 444 Karlsruhe features / 183 cases looks like "~2.4 geometries per case", and reasoning from that with the natural assumption of *one point per case* gives badly wrong conclusions. The actual shape: **222 Points and 222 non-Point geometries, exactly paired.** 159 cases carry one point + one shape; 24 cases carry 2–6 of *each* (a closure split across several street segments or building entrances). Types: `Polygon` 156, `MultiLineString` 36, `MultiPolygon` 22, `LineString` 8 — so **~20 % of shapes are line geometries, not areas**, which Leaflet draws as polylines that ignore `fillOpacity` entirely. `data/QUALITY.md`'s `hasArea` line tracks the ratio going forward; the type mix needs a fresh inspection run if it matters again.
- **What the shapes actually look like** (first full build with `area`, 183/183 cases): **no shape is an axis-aligned rectangle — 0 of 230 polygon rings.** They're oriented to the street. Vertices per ring: min 4, median 6, max 180; 114 rings have exactly 4 corners and 78 of those are right-angled, i.e. *rotated* rectangles (a lane or sidewalk strip), while 82 rings carry 11+ vertices and are genuine outlines. So a synthetic test fixture built from grid-aligned boxes looks nothing like production — if you fake `area` data for a browser check, rotate it, or you'll be reviewing a picture the app will never draw.
- **The WFS delivers *two* geometries per case, and both are now kept (A-7).** Before A-7 the dedup loop threw the polygon away; now `dedupeFeatures()` keeps the Point as `geometry` (marker position, unchanged) **and** *all* sibling non-Point geometries, combined by `buildArea()` into one `properties.area` (`MultiPolygon` if all polygonal, `MultiLineString` if all linear, `GeometryCollection` if mixed; a lone shape is left alone). Three things follow. (1) **`geometry` stays a `Point`, always** — `latLngOf()`, `haversineKm()`, the radius search, the filters, and the list all read the point and nothing else (E1 in A-7); putting a polygon in `geometry` would touch every one of them. (2) **`transformGeometry()` transforms unconditionally**, unlike `toWgs84()`, which auto-detects via `looksLikeUtm32`. `buildArea()` therefore does that check itself before calling it — drop the check and a source that unexpectedly answers in WGS84 gets its area mangled while its point comes through fine, i.e. a bug visible only on the map. (3) `properties.area` is the one **English** property name on a feature otherwise full of German ones (`titel`, `verursacher`, `ampel`) — deliberate (E7), new identifiers are English since 2026-07-27; don't "fix" the inconsistency in either direction.
- **Selection never moves the camera (A-11) — and Leaflet's popup `autoPan` silently overrides any `fitBounds` that precedes it.** Since A-11, `selectFeature()` contains no camera call at all: the popup opens, and its readability at the map edge is carried by Leaflet's default `autoPan` — a shift of at most the popup's height, never a zoom change. The machinery this replaced (fit to the area's bounds, `{ autoPan: false }` on area markers, `popupPlatz()`'s measured reserved strip — A-7/E5, #29) is deleted, but the trap it existed for is not: whoever re-adds a fit-then-open sequence will find autoPan pans the map so the popup sits at the **map** edge — a pan computed from popup and marker alone, landing in the same place no matter what the fit just did (measured back then: up to ~200 px, pushing 25–50 m of the just-fitted shape out of view). The working order was open-popup-first with `autoPan` off and the popup's real `offsetHeight` reserved as fit padding; reserving nothing **clips** the popup at the edge, which is worse than any shift. Symptom to recognise for the whole class: *identical* measured bounds before and after changing fit parameters means autoPan won, not that your change didn't apply. **Since A-14 part of the map is covered by chrome**, so autoPan is padded with what the search bar, the sheet/panel and the credits strip cover. The padding is set on every popup at bind time and refreshed by `setChromeInsets()` on every chrome change — setting it in a marker's click handler comes too late, because Leaflet's own click handler (registered by `bindPopup`) opens the popup first. Without the credits strip in the padding the *marker* ended up under the strip, popup visible, tip pointing at nothing. A list selection from a *full* sheet steps the sheet down to half; the sheet moves, the camera still doesn't. The three views that do move the camera (initial, search result, search reset) go through `setViewInVisibleArea()` in `src/ui/map.js`: same target, same zoom, centred in the uncovered map (A-14/E13 revised). Since A-17 there is a fourth: choosing a district fits its outline with `fitInVisibleArea()` — the chrome insets as padding, zoom 15 at most — and "Alle Stadtteile" returns to the initial view. A plain `setView()` lands its target 56–63 px too low on a phone and 206 px too far left on desktop, next to the panel.
- **The hover/selection tiers on the area layer (A-9) carry three traps.** (1) `render()` rebuilds rows, markers and areas from scratch, so any pointer-driven state must be torn down there (`setHoverKey(null)` at the top) or it survives as a ghost — the destroyed row's `mouseleave` never fires. (2) Hover is bound only when `matchMedia('(hover: hover)')` matches (a tap on iOS/Android leaves synthetic mouseover styling stuck until the next tap), while the focus path in `wireListFocus()` is deliberately **un**gated — a keyboard can hang off a touch-primary device. "Simplifying" both behind one gate silently takes the tabbing preview away from exactly those users. (3) `areaStyle()`'s tier argument must stay geometry-type aware and be applied **per child layer** (`_bauwatchTyp`) — a blanket `gruppe.setStyle()` would fill polylines and give polygons a 6-px stroke, and since line geometries (~20 % of shapes) ignore `fillOpacity` entirely, a fill-only ramp would emphasize nothing for them.
- **The sheet animates `height`, never `transform` (A-14/E3).** On a phone the search bar lives inside the panel's DOM and is lifted to the top of the screen with `position: fixed`; a transformed ancestor becomes the containing block of a fixed descendant and would drag the bar along with the sheet. The desktop collapse may use `transform` — the bar is static there. And every `dvh` height is declared after a `vh` one on the *property* itself: a fallback inside a custom property does not work (an unsupported value there makes `height` invalid at computed-value time, which falls back to `auto`, not to `vh`).
- **Sheet drags are heard on `window`, and the head is unselectable (A-14).** A mouse that leaves the head before the drag threshold goes silent unless moves are heard on `window` (touch is captured implicitly, a mouse is not). Pointer capture is no way out: it retargets the click after a plain tap away from the handle, and tap-to-cycle stops working. And a first drag selected the title text — the next press on the selection started a native drag-and-drop, which *cancels* the pointer stream mid-drag (`user-select: none` on `.panel-head`, `dragstart` prevented). Both only showed up by driving the sheet with a mouse in Playwright; the collapsed height is *measured* (`--sheet-collapsed`, a ResizeObserver on the head), never hardcoded — the credits footer rides on it.
- **`str('key')` is the only way the JS looks up UI strings (A-14/E11).** `scripts/test-i18n.mjs` checks every literal key against both dictionaries and fails a computed key (`str(someVar)`) or a direct `STRINGS[…]` outside `src/ui/text.js` — a computed handle label in `panel.js` was caught exactly that way. Spell keys out at the call site.
- **The UI guards read the client's module graph, not `src/app.js` (A-14 step 1).** `scripts/client-modules.mjs` follows the imports from the entry module; test-pwa (`SHELL` completeness), test-attribution, test-theme, test-changelog-feed and test-i18n use it. A new module must go into `SHELL`; a check on one function's body uses `functionBody()` (brace matching), never a slice up to a section comment — that slice became an empty, silently passing string the moment the comment moved. Of 11 seeded defects the old app.js-only guards caught 2, the graph-wide ones all 11.
- **A new feature property is invisible until the next real data change.** `diffFeatures()`/`signature()` compare all non-`_` properties, so adding `area` does count as a change and *does* trigger a write — but only on the next Action run, and the changed cases land in `data/CHANGELOG.md` with the generic note (the "Was ist neu?" feed drops them, per #28 — which is exactly right here: a schema addition is not news for a resident). The committed snapshot is therefore **behind the code** between merge and that run, and the client must tolerate it: `renderAreas()` skips a feature without `area`, `selectFeature()` falls back to today's `setView`. Adding a property that the client *requires* would need the snapshot rebuilt in the same commit — see the read-side-filter pitfall below for the mirror-image case.
- **Commit only on a real data change.** `build-data.mjs` compares against the previous snapshot and only writes/commits when features change. `stand` = the time of the last *change*, not of the last run. Consequence: the Git history of `data/baustellen.geojson` = real changes; many Action runs + few commits = changes are rare. **Never write per-run-volatile values into the file** (that creates noise commits and destroys this invariant).
- **Coordinate order:** GeoJSON is `[lon, lat]`, Leaflet expects `[lat, lng]`. The build has CRS auto-detection (`looksLikeUtm32`) and only transforms when values look like UTM meters.
- **The CC-BY attribution is static in `index.html` — not set via JS.** Since A-14 it sits in the credits `<footer>` on the map (with the OSM credit and the Impressum/Datenschutz links); the `<p id="attribution">` holds the attribution text and *nothing else* — the test compares the whole paragraph. It used to be an empty paragraph that `setFooter()` filled in after the data fetch: visible in the browser, not in the served document — and absent entirely on a failed fetch or without JavaScript. As a **license condition** it must not depend on any of that (the city's open-data editorial team noticed exactly this during the transparency-portal pre-review). The text is word-for-word identical to `ATTRIBUTION` in `scripts/build-data.mjs`; if one changes, the other must too. `scripts/test-attribution.mjs` checks the traps (empty attribution, any client module looking up `#attribution` at all — every write form starts with a lookup —, a `data-i18n` on it that the language switch would overwrite, drift from the build constant). Additions like the sample-data notice go through the separate paragraph `#attribution-hinweis`. Since A-17 the credits footer carries a second, static credit, `#attribution-stadtteile` (word for word `DISTRICTS_ATTRIBUTION` in `scripts/districts.mjs`, guarded the same way). It names no licence on purpose: the portal's metadata says CC0, GovData's listing CC BY 4.0, and the linked dataset page states the licence (A-17/E7 revised).
- **`--amber` is not a text color — still, even after #32 darkened it.** The traffic-light tokens in `src/styles.css` are tuned for dots and stripes on the page surfaces. As text, `--red` (~5.5:1) and `--green` (~5.0:1) meet WCAG AA in light mode, but `--amber` (`#cc7700` light since #32, `#ffb02e` dark) reaches only ~3.4:1 as light-mode text — enough for a *dot* (the 3:1 graphical-object bar, guarded token-by-token in `scripts/test-theme.mjs` section 8), not for text (4.5:1). For warning or emphasized text, use `--accent` or `--text` instead. **The map has its own tokens since A-14/E8:** `--map-voll/-teil/-gering/-search`, applied through CSS classes on the Leaflet paths — an identity class (`m-voll`…) plus a geometry class (`m-poly`, `m-line`, `m-marker`). A line gets no fill rule: CSS `fill` overrides Leaflet's `fill="none"` and would paint the polyline's hull (A-9's setStyle trap, in CSS form). The light values are exactly the old `AMPEL_COLOR` — `teil: #f08a00`, kept clearly lighter than Voll on the light tiles — so dot and marker still diverge in light mode; don't "sync" them. In dark mode the tiles are darkened (`--tile-filter`, a local CSS filter, same tile host) and the map takes the dark dot colours, measured against the median luminance of the darkened tiles: Voll 4.8:1, Teil 7.4:1, Gering 6.9:1, search 7.0:1. Known gap, pre-existing: light-mode Teil markers reach only 1.8:1 against the light tiles ([BACKLOG #37](docs/BACKLOG.md)). A chosen district's outline (A-17) has its own token, `--map-district` (violet `#6b2fa0` / `#b48ee8`, 5.9:1 and 5.1:1 against the tiles), in its own pane below the overlay pane. **The traffic-light triple is not a categorical palette (A-15).** Under protanopia, light-mode amber and green separate by only ΔE 7.4, so the three colours always appear with a word and a number beside them: in the filter buttons, and in the statistics tab's Sperrgrad bar and its legend. Every other chart uses the single neutral `--bar` (`--accent`'s value). Don't colour a new chart with the traffic light. **Calculate, don't estimate:** in the Playwright check, open one context with `colorScheme: 'light'` **and** one with `'dark'`, get the colors via `getComputedStyle`, and compute the WCAG ratio — a visual check in only one scheme cannot catch this violation at all. **Since A-8 the scheme is switchable**, so `colorScheme: 'dark'` on the context is no longer the same thing as "the page is dark": an explicit choice (`data-theme` on `<html>`) beats the context setting. When checking colors, either set the context scheme *and* leave the toggle alone, or click the toggle and ignore the context — reading `getComputedStyle(document.documentElement)` tells you which palette actually won.
- **`--bg` is the page background, not "the subtle surface."** Elements sitting on top (badges/chips) sit on `--surface` (list card), not on `--bg`. In light mode, `--bg` (#f7f7f5) happens to fit there *by coincidence* — it's a bit darker than the white card; in dark mode, `--bg` (#16181c) is **darker than** `--surface` (#1f2329), so the chip looks punched-out instead of resting on top (Backlog #22). That's why badges have their own tokens `--chip`/`--chip-border`. Pattern for new surfaces: pick or create a token by its role, not by whatever color value it happens to have in light mode — and check against the surface the element actually sits on, in **both** schemes. For dark chips, also pull the border along: `--border` (#333941) sits too close to the chip's tone and smears the edge.
- **`docs/BACKLOG.md` states status twice.** Besides the checkbox on the entry, the header has a `**Status:**` line and a "summary" that names individual numbers as open/done. Whoever only flips `⬜` → `✅` on the entry leaves a header that contradicts the entry — the same silent drift as with attribution and the privacy notice, just without a test here. A status change means: entry **and** header. (The opposite holds for `docs/anforderungen/` — there the overview is the *only* source of status.)
- **The `transform.js` reference test** checks against ground truth generated with `proj4`. `proj4` is **not a runtime dependency**, just a dev tool for generating the reference values.
- **GitHub Pages** deploys from `main`/root — every data commit goes live immediately. **Don't** switch to an Actions-based Pages deployment (that would serve snapshots → stale data). It's served under a **sub-path** `…github.io/BauWatch-KA/`, not at a domain root: paths in HTML/CSS/JS and in new assets must stay **relative** (`vendor/…`, not `/vendor/…`) — a leading `/` points at the `github.io` root and breaks silently.
- **`navigationAntwort()` in `sw.js` answered *every* navigation with `index.html` until A-4.** For a single-page app that was correct; with `impressum.html`/`datenschutz.html` it would have become a **silent bug** — installed clients would get the map page under `…/impressum.html`, with no error, and **locally this never shows up** (no old service worker registered). Since [ADR-002](docs/adr/ADR-002-mehrseitige-auslieferung.md), the function is **path-aware**: first the requested path from the shell cache, then network, `INDEX_URL` only as an offline fallback. Consequence: **every new HTML page must be in `SHELL`** (otherwise it's gone offline *and* not path-aware discoverable). `scripts/test-pwa.mjs` checks path-awareness statically and now scans **all** precached HTML pages for precache gaps, not just `index.html`.
- **The privacy notice is a claim about the code — and goes stale silently.** `scripts/test-rechtstexte.mjs` guards both directions: every external host from `src/*.js` must be named in `datenschutz.html` (build `routing.openstreetmap.de` for A-1 without updating it → `npm test` goes red), and as long as it states "no cookies / no own storage of personal data," neither `document.cookie`, `sessionStorage`, `indexedDB`, nor `navigator.geolocation` may show up in the frontend. Same drift logic as with attribution: a wrong privacy notice is worse than an incomplete one. The contact address is currently a **placeholder** (`kontakt@example.invalid`) — the test reports it as a `[WARN]` on every run until a real address lands in both pages.
- **`localStorage` gets a documented-key check, not an unconditional one (A-5/E6/ADR-003).** Since the DE/EN language toggle, `localStorage` is no longer categorically absent from the frontend — `test-rechtstexte.mjs`'s guard for it changed from "must not appear" into "every key found (`localStorage.getItem/setItem(...)`, resolved through a named constant like `SPRACHE_KEY` if needed) must be named in `datenschutz.html`'s 'Speicherung auf Ihrem Gerät' section." An *undocumented* key still fails the build; the other four storage checks (Cookies, `sessionStorage`, `indexedDB`, geolocation) stay unconditional, since they remain genuinely unused. Don't "fix" a red `test-rechtstexte.mjs` by weakening this back to unconditional — document the new key instead, same principle as the placeholder-address `WARN` below. **A-8/ADR-004 widened the exception** from one blessed key to a bounded *category* (anonymous display preferences, closed value set); there are now two keys (`bauwatch.sprache`, `bauwatch.theme`), and `test-theme.mjs` adds the value-level check — the *possible values* must be documented too, not just the key name. A new key of that kind no longer needs its own ADR, but it does need the privacy-notice entry.
- **The dark palette is deliberately written twice in `src/styles.css` (A-8) — don't "deduplicate" it.** It has to be reachable two ways: from `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` (nobody chose anything) and from `:root[data-theme="dark"]` (somebody did). CSS can't share one declaration block between a media query and a plain selector. Delete the media query and everyone who never touched the switch loses dark mode; delete the attribute block and the switch stops working. `scripts/test-theme.mjs` compares both blocks token-by-token and fails on drift, so *adding* a token means adding it to both. The same script guards the other three copies of a single fact: the `localStorage` key literal in `index.html`'s inline no-flash script vs. `THEME_KEY` in `src/ui/theme.js`, `THEME_COLOR` there vs. the `<meta name="theme-color">` pair, and the toggle buttons vs. `THEMES` (since A-14 checked by values and translated names, not by a fixed nesting — the toggle moved into the menu). The new map and shell tokens (`--map-*`, `--tile-filter`, `--float-shadow`, `--bar`) follow the same rule: all three blocks, light, system dark and chosen dark.
- **`index.html` has an inline `<script>` in `<head>` and it must stay there, before the stylesheet.** `src/app.js` is a module and therefore deferred — without those three lines, a visitor who chose dark gets a light flash on every load. It only reads the key and sets `data-theme`; anything else belongs in `app.js`. The legal pages are the opposite case: `impressum.html`/`datenschutz.html` must stay script-free (E6 in A-4, checked), which is exactly why they follow the system setting only and *don't* honor the toggle.
- **`impressum.html` and `datenschutz.html` stay German on purpose.** They're the actual site content for Karlsruhe residents, not internal docs — the 2026-07-27 docs-language switch to English covers `CLAUDE.md`/`README.md`/`docs/`, not the user-facing app itself. The manifest's `name`/`short_name`/`lang` fields stay German-only too (installed PWA identity). **`index.html`/`src/app.js` are the one exception**: since A-5, the interactive map page is bilingual via a DE/EN toggle (`src/lib/i18n.js`), German by default — see `docs/anforderungen/A-5-sprachumschalter.md` for the exact boundary (map shell in scope; legal pages, PWA identity, CC-BY attribution, and raw dataset text stay German-only, non-negotiably).
- **A guard must not permanently turn `npm test` red.** For a deliberately open item (placeholder address, still-missing detail), tie the test's strictness to the **documentation status**, not to a date or good intentions: as long as the relevant document lists the item as open, the test reports `[WARN]` and stays green; if the checkbox gets ticked there while the code still carries the placeholder, it fails hard. That way nothing goes live silently and the suite keeps its meaning.
- **A "this string must not appear here" guard also matches comments.** Several tests assert the *absence* of a literal (a second copy of the generic changelog note in any client module, `document.cookie`/`sessionStorage` in the frontend). An explanatory comment that quotes the string turns them red — that's correct behaviour, not a false positive, since the whole point is that the literal lives in exactly one place. Reference the **constant's name** in comments (`GENERIC_CHANGE_NOTE`), never its value.
- **Shell file changed → bump `CACHE_SHELL` in `sw.js`.** The service worker precaches the app shell (`index.html`, `src/*`, `vendor/leaflet/*`, `icons/*`, manifest) **cache-first and all-or-nothing per version**. Whoever touches one of these files without bumping the version serves installed clients the old version indefinitely — locally this never shows up. The `SHELL` list in `sw.js` is hand-maintained; a single typo in it makes `cache.addAll` fail entirely, and the SW then never installs. `scripts/test-pwa.mjs` checks both (existence of every entry, version in the cache name) plus the classic precache gap: every reference from `index.html` (except a short, named list of deliberate non-shell links — today only the Atom feed, A-2) **and** every module in the client's import graph (followed from `src/app.js` by `scripts/client-modules.mjs`, not just its direct imports) must be in `SHELL`. - **The feed shows *less* than `data/CHANGELOG.md`, on purpose (#28) — that asymmetry is the feature, not drift.** A case that changed only outside `WATCH_FIELDS` (coordinates, `art`, mode of transport) gets the fallback note `sonstige Angaben aktualisiert`. In `data/CHANGELOG.md` that belongs — it's the record of what the data did. In "Was ist neu?" it can't answer the app's question ("does this affect me?"), and whole runs consisted of nothing else. So `changelogEntry()` drops those changes, `build-data.mjs` skips an entry left empty by that (otherwise the feed shows a timestamp with an empty list), and the client (`src/ui/feed.js`, the "Neu" tab since A-14) filters again **on read** — that's what cleans the entries already committed inside the 30-day window and any copy an installed service worker still holds. Parity between the two artifacts is therefore **directional**: feed ⊆ Markdown, checked that way in `test-changelog-feed.mjs`. Don't "restore" the symmetry. The literal lives **once**, in `src/lib/changelog.js` — a shared pure module in the `transform.js`/`classify.js` sense (imported by the Node build *and* the browser), so it's bound by the same no-DOM/no-npm constraint and is in `SHELL`; a second copy of the string in any client module fails the test.
- **`data/changelog.json` (A-6) — same anti-drift/no-volatile-value rules as `CHANGELOG.md`/`QUALITY.md`.** Written by `build-data.mjs` in the same `hasChanges(diff)` branch as `prependChangelog()`, via the pure `changelogEntry()`/`pruneChangelogEntries()` helpers in `scripts/diff-data.mjs` (kept there, next to `summaryMarkdown()`, so the two artifacts can't drift). `stand` is the real change timestamp, never the run time — same invariant as `baustellen.geojson`'s own `stand`. Pruned to the last 30 days on every write; a `firstFill` run collapses to one synthetic `{ stand, firstFill: true, total }` entry instead of flooding the feed. `sw.js`'s data-path handling now covers **three** files (`DATA_PATHS` — `baustellen.geojson`, `changelog.json` and, since A-16, `history.json`), all network-first; `changelog.json` is deliberately **not** prefetched at service-worker install time (unlike `baustellen.geojson`) and is **not** part of `SHELL` — it's data, not shell.
- **The data workflow commits an explicit list of files (ADR-006).** `update-data.yml`'s commit step runs `git add` with each artifact named, and its gate (`git diff --quiet -- data/`) does not even see an untracked file. A new artifact the build writes is therefore never committed, and nothing reports it. Every new artifact goes onto that list in the same commit; `test-history.mjs` checks `data/history.json`, `test-feed.mjs` checks `feeds/alle.xml`.
- **`data/history.json` holds one value per day, and only counts the snapshot alone determines (A-16, ADR-006).** One entry per calendar day in Europe/Berlin (`berlinDate()` in `src/lib/stats.js`, shared by build and browser), the day's last snapshot wins, written in the same real-change branch as the snapshot, never pruned. The browser carries the last value forward over days without an entry (`fillHistory()`), because no entry means no change. Never add a date-relative figure ("ends within 7 days", a median duration): it changes at midnight without a data change, so recording it would need a write every day — a per-run-volatile value by another name. The file was seeded by `scripts/backfill-history.mjs` from the 247 snapshot commits since 2026-07-20 (91 days, no gap); the early snapshots of 2026-07-20 counted 440 features before the dedup fix, which end-of-day semantics absorb. A damaged file is left alone by the build (with a warning in the job summary) rather than replaced by a single day.
- **`feeds/alle.xml` (A-2) is generated from `changelog.json`, not from the diff.** One Atom entry per update run, the same entries as the "Neu" tab, so the parity is a chain: feed ⊆ `changelog.json` ⊆ `CHANGELOG.md`, and #28's filter, the 30-day window and the `firstFill` collapse apply to the feed for free. Every id and timestamp comes from `stand` (tag URIs like `tag:ahirrea.github.io,2026:BauWatch-KA/changes/<stand>`), so two generations from the same entries are byte-identical — a run time in the feed would be a noise commit. Links are absolute (`SITE_URL` in `scripts/feed.mjs`; Atom needs them, the sub-path rule is for the page). `<rights>` carries `ATTRIBUTION` word for word — a feed republishes the city's data, so the CC-BY condition travels with it (`test-attribution.mjs`). The service worker leaves the feed alone: not in `SHELL`, not in `DATA_PATHS`. `build-data.mjs` imports `scripts/feed.mjs`, and `feed.mjs` imports `build-data.mjs` back (for `ATTRIBUTION`) only dynamically, and never with a top-level await — awaiting that import while `feed.mjs` is still evaluating deadlocks the cycle (seen once: `node scripts/feed.mjs` exited 13 with "unsettled top-level await").
- **A site's district comes from the build, from its point (A-17, ADR-007).** `data/districts.geojson` is a committed static *input* — fetched once from the city's portal (see `fetch-districts.mjs` under Commands), WGS84, simplified at the finest tolerance of at least 1 m that changes no assignment (a 10 m first cut was too coarse: district boundaries run along streets, which is where sites are). The build assigns `properties.district` from the marker point with `assignDistrict()` (`scripts/districts.mjs`, point-in-polygon, nearest district within 100 m as fallback, else `null`); the browser only reads the property and draws the outline from the same file, so the two can never disagree about a boundary. `district` takes part in the diff signature on purpose (a boundary refresh that moves a site is a real change of what the app shows) — which is why the committed snapshot must be annotated (`annotate-districts.mjs`) whenever code and data meet, or the next run logs every case as changed. `changelog.json` items are `{ titel, district }` since A-17; entries written before are plain title strings, and every reader (the "Neu" tab, `feed.mjs`, the parity tests) takes both while they are in the 30-day window. The boundaries are precached shell (`SHELL`, cache-first), not a data path: they change only with a commit that bumps `CACHE_SHELL`.
- **Narrowing what a committed data artifact may contain needs a read-side filter too — and the existing file cleaned in the same commit.** `data/changelog.json` and `data/baustellen.geojson` are committed snapshots with their own retention (30 days) and are cached by the service worker, so a change to what the *build* emits stays invisible for up to that window — longer for installed clients. Pattern (#28): filter on write **and** on read through the same shared pure helper, then run the committed file through that helper in the same commit. A hand-touched data file is the deliberate exception to "data commits come from the Action"; the alternative is shipping a repo whose data contradicts the app.
- **The numbers in the Sperrgrad buttons are counted over a *different* set than the list (A-12/E3), and `render()` is where that gets silently broken.** `render()` builds two arrays: `filteredBase()` (restdauer + Verkehrsmittel + Umkreis) feeds `renderFilterCounts()`, and `applyAmpel(base)` feeds map, list and status line. Passing `list` to `renderFilterCounts()` instead is a one-word change that compiles, looks tidier, and produces a button captioned "0 Teil" that delivers 118 hits — because with `Voll` active the other two levels are 0 *by definition*. The whole point of the facet count is that the numbers stand still while you toggle between the three levels; they may only move on Restdauer, Verkehrsmittel or Umkreissuche. Two related traps: a count of 0 must **not** hide its button (A-10/E6 was written for a passive strip and is superseded — a control that vanishes at 0 is missing exactly when you want to get back), and before `state.geladen` the buttons must stay unbeziffert, since a "0" then is indistinguishable from a real zero. The regression is invisible to `npm test` — `scripts/test-stats.mjs` can only check `summarize()`, which counts whatever it is handed; only the browser check catches it. **Since A-17 there are two faceted controls**, and the rule holds per control: the Sperrgrad numbers count everything but Sperrgrad (the district included — `filteredBase()`), the district select's numbers count everything but the district (`districtCounts()`) — and not the radius search either, because choosing a district clears the search (A-17/E5), so a count inside the radius would promise a number the click does not deliver.
- **A filter can be dead against the live data and no test will ever say so (A-12).** The "Zeitraum" filter shipped for months while three of its four options returned the identical set and the fourth returned 0 — because the WFS publishes *currently running* cases only, so nothing starts in the future and nothing has ended. `matchesZeitraum()` was correct code; the axis it filtered on was constant in the data. Nothing in `npm test` can see that (the fixtures are hand-made and do contain future dates), and the browser check would have passed too. What finds it is running the predicate across the committed snapshots: `git log -- data/baustellen.geojson` gives ~86 of them, and each one is a real, dated sample. Do that before trusting any filter that "looks fine". The recurrence is guarded from the other side: `data/QUALITY.md` now reports "beginnt erst später" (A-12/E6), so if the city ever extends the dataset it shows up in a committed artifact instead of nobody noticing.
- **`data/QUALITY.md`'s `hasArea` line is an observation, not a defect count (A-7/E9).** Every other block in the quality report lists something *wrong* with the city's data; "Vorgänge mit Fläche" / "Vorgänge ohne Fläche" just reports the geometry mix, because whether a case really pairs one point with one polygon **can't be checked outside an Action run** (egress). So don't fold `ohneFlaeche.length` into `summarizeQuality()`'s `problems` total — a point-only case renders exactly as it did before A-7. `mitFlaeche` is derived (`total − ohneFlaeche.length`), and `test-quality.mjs` asserts the two add up to `total`, so a future `hasArea` change can't silently produce a ratio that means nothing. **`dateIssues.startetSpaeter` (A-12/E6) follows the same rule** — it exists so a change in what the WFS delivers becomes visible, not because a case starting next month is wrong; `test-quality.mjs` asserts that adding such a case leaves `problems` unmoved.
- **The service worker is only testable via `localhost`** (secure context) — `file://` doesn't register. Playwright pattern: `context.setOffline(true)` does **not** reach `fetch` calls from inside the service worker (its own network context); for a real offline test, cut off same-origin via `context.route(…, r => r.abort())`. The update-banner path can be run end-to-end by copying the project to the scratchpad, serving from there, and bumping `CACHE_SHELL` in the copy.
- **The very first page load bypasses the service worker** (no `controller` yet) — that's why the `install` handler loads `data/baustellen.geojson` into the data cache once, itself. Without this step, after a single visit the shell would be ready offline but not a single construction site would be.
- **No `push`/`notificationclick`/`sync` handler in the SW.** The SW is the technical prerequisite for push — the non-goal "no real push" (decided in `A-2`) still holds; `scripts/test-pwa.mjs` checks the absence of these handlers.
- **Sample-data starting value:** `data/baustellen.geojson` can carry `sample: true`; the first real Action run replaces it (`firstFill` logic).
- **The data Action commits to `main` itself.** After a manually triggered run (or while working in parallel), the local state goes stale quickly — before the next push, run `git pull --rebase origin main`, or the push gets rejected with "fetch first".
- **The real WFS structure can only be checked via an Action run** (local fetch is blocked by egress) — but a *new* workflow can't be dispatched to do it: the API only dispatches workflows present on the **default branch**, so a temporary one added on a feature branch answers `404`. What works is dispatching the already-registered `update-data.yml` with `ref=<branch>`, which runs **that branch's copy** of the file: put the inspection step in there temporarily, read the job logs, then reset the file to `main`'s version. Editing it on a branch is safe — `schedule` runs always use `main`'s copy. Two further consequences. Its commit step pushes to the checked-out ref, so the same trick **seeds the feature branch with a real snapshot**, which is how to close the "committed data is behind the code" gap *before* merge rather than after. And conversely, a scheduled run never exercises unmerged code — "let's wait for the next Action run" yields nothing until the branch lands.

## Testing the frontend in a browser

`playwright-core` is installed; Chromium lives under `/opt/pw-browsers/chromium-*/chrome-linux/chrome` (with `--no-sandbox`). **Glob it, don't hardcode the build number** — the pinned `@playwright/test` version and the image's Chromium build drift apart, and a stale path fails with "executable doesn't exist". Pattern: start a local `http.server`, load the page, wait for `#liste li` — with `{ state: 'attached' }` on a phone viewport, where the list starts inside the collapsed sheet (see the sheet bullet below). In environments without egress, intercept OSM tiles via `page.route('**://tile.openstreetmap.org/**', r => r.abort())` — the map then stays gray, markers/list/filters still work (markers are SVG `circleMarker`s, they don't need tiles). **Real tiles for screenshots:** some cloud environments block the bare `tile.openstreetmap.org` but allow `a.tile.openstreetmap.org`; rewrite on the test side with `context.route('https://tile.openstreetmap.org/**', r => r.continue({ url: r.request().url().replace('://tile.', '://a.tile.') }))` — never in the app, whose privacy notice names the bare host. That is how A-14's dark-map contrast was measured against what users actually see.

Two traps when asserting on the map's SVG (both cost a debugging round during A-7):

- **`#map svg path` is not "the map's shapes."** Leaflet's attribution control carried a three-`<path>` Ukraine-flag SVG, so a count over that selector was off by three; since A-14 the control is off (the credit is static HTML), but scope to **`.leaflet-overlay-pane svg path`** anyway. Separate markers from areas by `classList.contains('leaflet-interactive')` — the area layer is `interactive:false` (A-7/E3) and therefore has no such class, which is also the cheapest way to *check* E3 — or, since A-14, by the geometry classes `m-marker` / `m-poly` / `m-line`. Colours are CSS now: read them with `getComputedStyle(path).fill`, not from the `fill` attribute.
- **Don't infer zoom from pixel sizes.** `src/ui/map.js` keeps the Leaflet map in a module-scoped `map`, invisible to `page.evaluate`. Rather than measuring a shape's on-screen width (fragile — the widest shape after a `fitBounds` is often a *neighbouring* one), grab the instance from the test side with `page.addInitScript()` wrapping `L.map` to stash it on `window`: then `getZoom()`/`getBounds()` answer directly, which is what made A-7's `maxZoom:17` cap assertable and now makes A-11's "selection never changes the zoom" rule assertable. The app stays untouched.
- **Compare pan/zoom against the `before/` checkout, not against intuition.** Leaflet's popup `autoPan` shifts the centre when the popup wouldn't fit, so "selection didn't centre exactly on the marker" can be pre-existing behaviour that depends only on the zoom you happened to arrive at. Load both checkouts from the same start view and diff `getCenter()`/`getZoom()`.
- **There is no "deselect" — so a before/after shot of one shape needs a *fresh page*, not a second selection.** Capturing A-9's idle-vs-hover-vs-selected ramp from one identical view, the obvious move is: select the target (that's what fits the view), then select something else to clear it, then restore the view with `setView()`. It produces a picture in which the *neighbour* is the emphasized shape, and reading that strip suggests the wrong feature got highlighted. Load a second page instead, `setView()` straight to the recorded view, and hover from there — nothing is selected at all. More generally: assert per frame *which* group carries the non-idle style (read `stroke-width`/`fill-opacity` off the paths) rather than trusting the eye; two of these strips looked like a code bug and were a capture flaw.
- **Never select a list item by title substring.** Construction-site titles are not unique (several `vorgangsnummer` share one street description) and the default "heute aktiv" filter hides some, so `innerText.includes(title)` can click a *different* feature — and then a geometry assertion measures a shape that was never selected and reads as a code bug. Resolve the target to a **list index** in-page, require the title to be unique both in the rendered list and in the data, and assert afterwards that `#liste li.is-selected` really is the intended one. Same discipline for the map: when a check disagrees with what the code plainly does, patch `L.Map.prototype.fitBounds`/`setView` from `addInitScript` to log what they actually received before touching `src/app.js` — twice during A-7 that turned an apparent bug into a test flaw (and once into a real one).
- **Styling a `<dialog>`, always check the *closed* state — and never set `display` outside `[open]`.** The closed dialog is hidden only by the UA rule `dialog:not([open]) { display: none }`, and **author styles beat the UA origin regardless of specificity**, so a `.whats-new-dialog { display: flex }` doesn't just lay out the open dialog: it makes the closed one appear in the normal flow, unopened, with no backdrop, half-covered by the map that follows it in the DOM. That went live once (#34) because every single check — probes and screenshots alike — clicked the button first, and an opened dialog looks perfect either way. So put `display` on `.whats-new-dialog[open]` — since A-14 the feed is a tab and the one dialog is the ☰ menu, same rule: `display` only on `dialog.menu[open]` — and end any dialog check with a closed-state pass: `getComputedStyle(dialog).display === 'none'`, a 0 × 0 client rect, and the initial page screenshot byte-identical to the `before/` checkout. For that last one the tiles have to be *genuinely* intercepted: the app requests `tile.openstreetmap.org` **without** a subdomain, so the glob `**://*.tile.openstreetmap.org/**` silently misses it (use `**tile.openstreetmap.org/**`) and the live tiles alone put 632 differing pixels into a diff that is otherwise byte-identical — enough noise to hide a real layout shift, and enough to send you looking for one that isn't there.
- **Moving an element in the DOM changes text antialiasing on its new siblings — so "byte-identical screenshot" is the wrong parity check for a layout move (A-13).** Relocating `<section class="filters">` into `<main>` left every box identical to **0.01 px** (`#map` 277.89/560.00, `.liste` 317.08/520.81, before and after) and still produced **5601 differing pixels of 4 096 000** at 1280 × 800, `maxDelta` 76 — all of them glyph edges inside the list text, none in the map, the filter row or any control, and the crops are visually indistinguishable. It is not noise: screenshotting the *same* page twice diffs to **0**, so the cause is the changed paint order (the list gained a `<section>` sibling), which flips Chromium between subpixel and greyscale rasterisation for some glyphs. Two consequences. Assert **fractional** geometry (`getBoundingClientRect()` unrounded, two decimals) rather than pixels — that is the claim that actually means "the layout did not move", and rounding to integers hides a real 0.5 px shift while a pixel diff flags a non-shift. And when a pixel diff is used anyway, always run the control (same page, twice) first: without it, 5601 red pixels look like a bug and cost a round of hunting for one that isn't there.
- **A scrollbar bug is invisible in a headless screenshot, and `clientWidth` won't find it either.** Headless Chromium draws *overlay* scrollbars, so #34's two side-by-side bars simply weren't in the picture, and the usual probe for "does this box have a bar" (`offsetWidth - clientWidth - borders`) read `0` for both the broken and the fixed state. Two ways out, both needed: measure the **scrollable range** (`el.scrollHeight - el.clientHeight`, plus whether a `page.mouse.wheel` over a non-scrolling part of the frame actually moves `scrollTop`), and take the before/after shots with `chromium.launch({ headless: false })` — a headed window on Windows uses classic bars and reproduces what the reporter saw.
- **On a phone the list lives in a sheet, so "visible" and "there" part ways (A-14).** Collapsed, the sheet shows only its head: `#liste li` is attached but not visible, and Playwright's default `waitForSelector` (state `visible`) times out. Wait for `attached`, then open the sheet (`#sheet-handle`, or a tab) before clicking a row, and pick hover/click targets among rows that are actually inside `#panel-body`'s visible box — the first row is often under the filter row's edge or already selected. A marker click scrolls its row into view *smoothly*: assert `scrollTop` after ~1.5 s, not on the next frame. A drag snaps to the **nearest** state, so a "drag up a bit" test lands on half, not full; test "released nearer half" and "dragged to the top" separately. And `#map`'s box is the whole viewport now, so it says nothing about what is visible — measure the uncovered area from `#searchbar`, `#panel` and `#map-credits`, or read a target's container point through the `L.map` handle (above) and compare it with the canvas centre.

## Web/mobile workflow (Claude Code on the web)

This repo is often worked on from a **cloud session** (claude.ai/code, including from a phone/the Claude app). On a small screen, typing and reading diffs are the bottleneck, not compute time — the following points are geared toward that:

- **Have it verified instead of scrolling diffs.** Phrase the task so Claude runs `npm test` **and** a Playwright browser check itself and only reports the result ("N/N checks green"). Pure, DOM-free logic changes in `src/lib/` are covered by `npm test`; UI/`app.js` changes additionally get checked in the browser (see "Testing the frontend in a browser"). For **doc restructuring** (moving/splitting `.md` files), `npm test` says nothing — check mechanically instead: all relative links still resolve, and no text was lost while splitting (compare sentence counts old↔new, report only intended deviations).
- **Always send screenshots along with UI changes** — unprompted, as part of the result report (explicit wish of the idea's originator). On a small screen, an image is grasped faster than any description, and visual findings ("looks punched-out") can only be signed off visually. Practice: generate Playwright screenshots in the scratchpad and send them via `SendUserFile` — **mobile (414 px) and desktop (1280 px), each light and dark** (`colorScheme`), plus a close-up of the changed element (`locator(…).screenshot()`, `deviceScaleFactor: 3`). Intercept tiles while doing so (see above) and mention when reporting that the gray map is due to that. The screenshots do **not** replace the computed contrast values, they come in addition. For a change that *removes* or filters something, a genuine before-shot is worth the extra minute: `git archive HEAD | tar -x -C <scratchpad>/before` gives an unmodified pre-change checkout, served on a second port and screenshotted with the same locator. The same trick serves the **old** data file against the **new** code — that's how you prove a read-side filter really cleans already-committed entries, instead of asserting it.
- **`node_modules` is not shipped** and is empty in fresh sessions. Before browser checks: `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install` (Chromium is already there, no need to redownload). **Afterward, remove `node_modules` again and don't commit `package*.json`** if the install touched them — they don't belong in a feature commit.
- **Temporary scripts** (e.g. verification runners) go in the scratchpad — there, import `playwright-core` via an **absolute path** (`<repo>/node_modules/playwright-core/index.mjs`). Starting from the project directory does **not** help — ESM resolves bare specifiers relative to the importing file, not to the working directory (and `NODE_PATH` doesn't apply to ESM either). Clean up afterward, never commit.
- **Mind egress.** `build:data` needs `mobil.trk.de`, radius search needs `nominatim.openstreetmap.org`, the map needs `tile.openstreetmap.org` — blocked or not depending on the environment's network policy. Intercept tiles in tests (see above); for real data runs, allow the domain in the environment's network config under "Network access → Custom", or use the GitHub Action.
- **Recommended environment configuration.** For everyday work (changing code, `npm test`, a Playwright check with intercepted tiles, committing/pushing), **Trusted** is enough — npm, GitHub, and `raw.githubusercontent.com` are in the default allowlist. Only someone running `build:data` or the live map/radius search **directly in the web session** needs **Custom** with `mobil.trk.de`, `nominatim.openstreetmap.org`, `*.tile.openstreetmap.org` (checkbox "include defaults" **on**, or `npm install` breaks). The Custom tier is only selectable via the web UI, not in the mobile "create environment" dialog.
- **Env variables: none needed.** The project uses no secrets/API keys (WFS/Nominatim/OSM are public; the only `process.env` use is the Action's built-in `GITHUB_STEP_SUMMARY`). The Playwright variables are already set by the platform image.
- **Setup script (optional):** `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install || true` pre-installs the dev deps so browser checks run immediately without manual installing. **`npm install`, not `npm ci`** — `package-lock.json` is gitignored and missing in fresh sessions. No commit risk: `node_modules/` and the lockfile are gitignored, `npm install` doesn't touch `package.json`. `npm test` itself needs no `node_modules` (plain Node scripts), the pre-install only matters for the browser checks.
- **Teleport to the right device.** On the laptop, `claude --teleport` pulls the phone session — including branch and history — into the terminal — prerequisite: same claude.ai account, clean git state, and **the branch is pushed** (the VM clones from GitHub). So: commit and push work before switching.
- **`main` moves under you.** The data Action commits to `main` itself; before pushing to `main`, always `git fetch origin main` first and rebase/cherry-pick your own commit onto it (no force-push needed if only genuinely new work is added). **Pull requests are unusual here** — finished work lands directly on `main`. Clean path for "commit directly to main" on request: commit on the feature branch, `git fetch origin main`, then **fast-forward** (`git merge --ff-only <branch>`) and push — no merge commit (the one in the history is an accidental `git pull`).
